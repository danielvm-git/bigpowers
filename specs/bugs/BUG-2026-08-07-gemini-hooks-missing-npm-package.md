# BUG-2026-08-07: npm tarball excludes .gemini and .cursor — Gemini install fails with "Hook source missing"

## Problem

- **Actual**: On a genuine global npm install (`npm install -g bigpowers@latest`), `bigpowers update` installs 81 skills to most runtimes but **Gemini fails**: `✗ Gemini — Hook source missing: <pkg>/.gemini/extensions/bigpowers/hooks/session-start (expected under repo skills/ or scripts/hooks/; fix path or restore file)`. The installer exits with "Some installations failed."
- **Expected**: All selected targets (including Gemini) install cleanly from the npm tarball, exactly as they do from a git checkout.
- **Reproduce**: `npm unlink bigpowers && npm install -g bigpowers@latest && bigpowers update` on a machine with `~/.gemini` present → Gemini target fails on the hook link. Also provable without installing: `npm pack --dry-run --json` shows **0** files under `.gemini/` (and 0 under `.cursor/`) in the tarball.

**Security impact: NONE** — no exploit path; the defect only breaks the Gemini (and potentially Cursor) install targets for npm consumers.

## Root Cause Analysis

### Reproduce

`npm pack --dry-run` on the repo → tarball contains 9,877 files, of which **0** are under `.gemini/` and **0** under `.cursor/`. Installing that tarball globally and running `bigpowers update` reproduces the `Hook source missing` failure at the Gemini step.

### Isolate

`.npmignore` lines 3–4 exclude `.cursor` and `.gemini`. `bin/setup.js` runs `sync-skills.sh --distribute-only` during update, which regenerates `.cursor/rules` and `.gemini/extensions/bigpowers/{skills,commands}` from the `skills/` sources — so those trees *appear* after the sync step. But `.gemini/extensions/bigpowers/hooks/` (8 committed files: `session-start`, `run-hook.cmd`, `before-tool-*.sh`, `settings.json.example`, etc.) is **not regenerated by sync** — it is a generated-then-checked-in artifact. Nothing in the npm install path creates it, so `install_gemini`'s hook links (install-targets-a.sh) throw on the existence check in `scripts/lib/install-helpers.js` (`linkHook`).

### Hypothesize

Removing `.gemini` (and `.cursor`) from `.npmignore` makes the tarball carry the committed hook tree, so the Gemini install target finds its hook sources — the same way `.pi/skills` (485 files) already ships. Verified against the failure mode: the only missing piece on a tarball install is the hooks directory; skills/commands/rules are regenerated by the setup-time sync.

### Verify

`npm pack --dry-run` after the change shows `.gemini/extensions/bigpowers/hooks/session-start` (and all 8 hook files) in the tarball; a tarball install then completes the Gemini target.

**Contributing factors**: (1) `.npmignore` was written to slim the tarball (specs/, docs/, website/ also excluded) without accounting for artifacts the installer hard-links from the package root; (2) `linkHook` is a hard failure rather than a warn-and-skip; (3) the setup-time sync partially masks the defect by regenerating skills/commands/rules — only the committed hooks remain missing.

**Prior art**: BUG-2026-06-24T045323 ("npm install fails during postinstall — docs/ excluded from tarball") — same defect class: `.npmignore` stripping a path the package needs at install time.

**Risk level**: High — every npm consumer with Gemini CLI gets a broken Gemini install; Cursor's per-project note (`ln -sfn <pkg>/.cursor/rules .cursor/rules`) likewise references a path absent from the tarball.
