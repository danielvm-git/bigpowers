# BUG-2026-07-03T020000: release-branch does not verify CI completion before declaring success

## Problem

**Actual behavior:** `release-branch` pushes to main, then declares success immediately without waiting for CI workflows to complete. Step 7b says "See REFERENCE.md" but the agent is not instructed to actually poll and wait.

**Expected behavior:** After pushing or merging, release-branch MUST poll GitHub Actions until all workflow runs for the pushed commit complete with `success`. If any workflow fails, hand off to `fix-bug`. If CI exceeds a configurable timeout, report the timeout. Only after all workflows are green should `release.ci_verified: true` be written to `state.yaml`.

**How to reproduce:**
1. Complete any story via `build-epic`
2. Run `release-branch` to merge to main
3. Observe that Step 7b says "CI workflow passes after push ✅" as a checkbox, but no actual polling occurs

## Root Cause Analysis

Three defects compound into a single observable failure:

**Defect 1 — CI polling logic is buried in REFERENCE.md, not promoted to a standalone script.** The REFERENCE.md contains a 34-line bash snippet (lines 124-159) that correctly polls `gh run list`, checks status/conclusion, and handles success/failure/timeout. But it lives in a reference document that the agent has to manually read and interpret. The main SKILL.md Step 7b says "See REFERENCE.md" — no explicit instruction to execute the polling loop. Agents following the SKILL.md linearly never reach the polling logic.

**Defect 2 — Hard-coded workflow name `--workflow CI` matches no actual workflow.** The polling snippet uses `gh run list --workflow CI`. The repo's actual workflows are named "Sync Skills on Push" (`sync-skills.yml`) and "Release" (`publish.yml`). The poll would return zero results and timeout, even if correctly invoked. This defect means the script never worked — it was written against a workflow name that doesn't exist in this repository.

**Defect 3 — No git-only fallback when `gh` CLI is unavailable.** The polling logic depends entirely on `gh run list` and `gh repo view`. If the GitHub CLI is not authenticated or not installed, Step 7b has no alternative path. The requirement states "using gh if available or using git command" — the git fallback is not implemented.

**Contributing factors:**
- The `release-branch` skill is 144 lines with a 160-line REFERENCE.md. The CI verification logic is the only step gated behind a reference document — all other steps have inline instructions.
- The `--workflow CI` name suggests the script was templated from another project and never adapted to this repo's workflow names.
- Workspace runs show: "Release" workflow has both success and failure runs, "Sync Skills on Push" has success runs. A real CI poll would have caught the failures before declaring release complete.

**Risk level:** MEDIUM — does not cause data loss or code corruption, but silently allows releases to land without CI verification, defeating the entire quality gate infrastructure being built in e31 and tested in e37.
