### 1. Business narrative
build-receipts.sh (e41s01) aggregates quality evidence into specs/receipts.json,
and the receipts page renders it (e41s02). But without CI wiring, the receipts
stale — the published page reflects whatever was committed, not the current
state of evidence artifacts. This story wires build-receipts.sh into the docs-site
CI workflow so every push to main regenerates receipts before the Astro build,
ensuring the published page always reflects the current commit. The gate follows
the e40 provenance rule: check that the generator RAN and receipts.json parses,
never gate on a specific metric value.

### 2. Value statement
As a site visitor, I want the /receipts page to reflect the most recent evidence,
so that I'm not looking at stale numbers from a previous release.

### 3. Actors and permissions
- CI runner (system) — executes build-receipts.sh in GitHub Actions.
- Release engineer (internal) — configures the workflow.

### 4. Trigger and preconditions
Trigger: push to main (via docs-site workflow).
Precondition: build-receipts.sh exists and is executable.
Precondition: e28 docs site workflow exists (.github/workflows/docs-site.yml).

### 5. Main flow and business logic
1. docs-site workflow triggers on push to main.
2. Before Astro build: execute bash scripts/build-receipts.sh.
3. Verify receipts.json was generated and parses (provenance gate — not value gate).
4. Proceed with Astro build, which reads receipts.json at build time.
5. Deploy updated site with fresh receipts.

### 6. Alternative flows and exceptions
6a. build-receipts.sh fails — workflow fails, site build halted.
6b. receipts.json fails to parse — workflow fails with clear error.
6c. Evidence sources partially missing — build-receipts.sh handles gracefully (source: absent), workflow passes.

### 7. Interface elements
Context: existing (.github/workflows/docs-site.yml).
Static elements: build-receipts.sh step before Astro build.
Dynamic elements: receipts.json freshness timestamp updated on each run.

### 8. Domain model
Entities modified: .github/workflows/docs-site.yml (new step).
Entities read: specs/receipts.json (generated by build-receipts.sh).

### 9. Integrations and boundaries
- build-receipts.sh (direction: out) — invoked before Astro build.
- e28 docs site workflow (direction: in/out) — modified to include receipts step.
- e41s01 build-receipts.sh (direction: in) — prerequisite.
- e40 provenance gate pattern (direction: in) — design rule.

### 10. Background processes
Not applicable — CI workflow is synchronous.

### 11. Notifications
- CI failure notification (GitHub-native) if build-receipts.sh or receipts.json fails.

### 12. Audit and logging
- CI run logs capture build-receipts.sh output.
- receipts.json carries generated_at timestamp for freshness audit.

### 13. Solution variabilities
- Workflow trigger (config) — currently on push to main; could add schedule/weekly.
- Gate strictness (config) — provenance-only (e40 rule), could add value sanity bounds.

### 14. Quality attributes *NFR*
- Workflow step: < 10 seconds (build-receipts.sh reads local files only).
- Deterministic: same state → same receipts.json every run.

### 15. Security and compliance *NFR*
- Read-only access to repo files — no secrets needed for evidence aggregation.
- No API calls in build-receipts.sh (local file reads only).

### 16. UX and accessibility *NFR*
Not applicable — CI automation, no user interface.

### 17. Acceptance criteria
Scenario: Fresh receipts on push (happy path)
  GIVEN a push to main
  WHEN the docs-site workflow runs
  THEN build-receipts.sh executes before the Astro build
  AND the step succeeds
  AND receipts.json is regenerated with current evidence

Scenario: Generator fails (6a)
  GIVEN build-receipts.sh exits non-zero
  WHEN the workflow runs
  THEN the workflow fails
  AND the site build does not proceed

Scenario: Parse failure (6b)
  GIVEN build-receipts.sh produces invalid JSON
  WHEN the workflow validates receipts.json
  THEN the workflow fails with parse error message

### 18. Out of scope
- Adding receipts to workflows other than docs-site.
- Gating on metric values (provenance-only gate per e40 design).
- Auto-committing receipts.json back to the repo.

### 19. Open questions
- Should receipts.json be committed to the repo or generated at build time only?
  Current design: generated at build time, not committed. This means receipts are
  only live on the site, not in the repo. Trade-off: git history vs freshness.
